# Design notes: document pipeline, chat memory, dashboard (2026-08)

A short tour of how the system's shape evolved this month, for a new
contributor (or the project owner returning after a break) to read in a few
minutes. This is deliberately referential, not exhaustive - it links out to
`docs/security_design.md` and `AGENTS.md` rather than re-explaining what's
already documented there, and to specific files rather than reproducing
their APIs.

## Document pipeline

Flow: **upload → classify → extract → store** (`src/data_ingestion/`,
`src/data_extraction/`). Classification is keyword-first (fast, free,
deterministic) with an LLM fallback for documents that don't match any
category's keyword list; see `src/data_extraction/classifier.py`. Whatever
category is chosen (or "other"), the same LLM-based extractor
(`src/data_extraction/extractor.py`) pulls structured fields (provider,
statement period, total, line items) using the category's field list as a
schema hint. Both the category and the extraction result are written into
the *same* encrypted vault record as the raw upload - there is no separate
store for structured data (see `docs/security_design.md`'s "Document-category
pipeline" and "Multi-session chat and dashboard" sections for the exact
vault-key/plaintext implications).

**Adding a new category** (a new utility provider, a new card issuer, a new
document type entirely) means adding one `Category` entry to `CATEGORIES` in
`src/data_extraction/categories.py` - keywords, and the metadata fields to
show on the Upload form. That one entry drives classification, the Upload
form, structured-record filtering (`ChatEngine.get_structured_records`), and
the Dashboard/Files-page category groupings simultaneously. See
`AGENTS.md`'s "Before making a change" checklist - don't hand-roll a
separate classifier/extractor code path per category.

## RAG vs. structured datastore: why both exist

`ChatEngine._build_prompt` (`src/ai_engine/chat_engine.py`) tries, in order:

1. **Structured aggregation** - if the query names a document category
   (`query_analysis.detect_category_from_query`), pull the actual extracted
   numbers for matching documents (optionally date-scoped via
   `parse_relative_date_range`) and have the model compute from those exact
   values.
2. **Category-scoped RAG** - a category was named but no structured records
   matched (or none exist yet): vector search scoped to that category via
   ChromaDB's `where` filter.
3. **Plain RAG / no-RAG** - no category detected, or `use_rag=False`.

This isn't RAG-being-replaced-by-structured-extraction; it's two
complementary retrieval paths for two different question shapes. RAG is
good at open-ended, fuzzy, "what does this document say about X" questions
but bad at numeric aggregation - "how much did I pay T-Mobile last month"
requires exact addition over exact fields, not a summary of whatever
semantically-similar chunks happen to get retrieved. Structured extraction
gives the model exact numbers to compute from instead of asking it to do
arithmetic over prose.

Both structured lookup and RAG do the same thing architecturally: decrypt
vault records and scan them in Python (`get_structured_records`,
`_load_vault_data_for_rag`), because **the vault has no native query
engine** - values are opaque encrypted blobs keyed by storage key. That's an
explicit, accepted tradeoff at personal-data scale (hundreds, not millions,
of documents), not an oversight; see `docs/security_design.md`'s "RAG /
ChromaDB" section for the same rationale applied to why a second,
separately-secured index wasn't built instead.

## Chat context management

- **Real history**: `history` (chronological, oldest-first) is now threaded
  into every prompt path and shares the same overall character budget as
  RAG/structured context (context gets first claim on up to 70% of what's
  left after system-prompt/query/reply headroom; history gets the rest).
  `ChatEngine._fit_history_to_budget` drops oldest messages first when the
  budget is exceeded.
- **`num_ctx` wiring**: `OllamaClient.context_window_tokens`
  (`PERSONAL_AI_CONTEXT_WINDOW_TOKENS`) is passed as `num_ctx` on every
  `chat()` call, and `ChatEngine`'s own budget math reads that same value -
  no more silent disagreement between what the app assumes and what Ollama
  is configured to use.
- **The context meter**: `ChatEngine.estimate_usage(history,
  pending_context="")` is a pure computation (no vault/RAG/Ollama calls)
  returning `used_tokens`/`budget_tokens`/`ratio`, driving a progress-bar
  meter in the chat UI. It warns at **75%** and again more urgently at
  **90%** full. The recommended action once it's full is to **start a new
  chat** rather than trying to "clean up" the current one - a fresh session
  gets a full budget again, since budgeting is per-session (each session's
  history lives at its own `chat_history_<session_id>` vault key).
- **Session lifecycle**: sessions are created/switched/deleted through
  `src/interface/chat_sessions.py`, backed by one vault index record
  (`chat_sessions_index`) plus one vault key per session's messages. A
  legacy single-conversation vault (from before multi-session existed) is
  auto-migrated into a session titled "Previous Chat" the first time the
  chat page loads, in place (no message copying).

## Dashboard

`src/interface/dashboard.py` defines an ordered `WIDGETS` registry -
`(widget_key, display_label, render_fn)` tuples, each `render_fn` consuming
the same `records` list (built once per page load from all non-internal
vault keys) and calling into pure, independently-tested aggregation helpers
in `dashboard_data.py`. **Adding a widget** means writing one `render_fn`
(taking `records`, calling `st.*` to draw) and appending one tuple to
`WIDGETS` - no other wiring required. Which widgets are visible is
user-configurable via a multiselect, persisted to the `dashboard_config`
vault key (`{"enabled_widgets": [...]}`, defaulting to "all" if unset or
unreadable).

## File organization/lifecycle

The Files page groups uploaded documents by category
(`src/interface/file_grouping.py`'s `group_files_by_category`), ordered to
match `CATEGORIES` with "other"/uncategorized last and empty categories
omitted from view. Each file also has a re-categorize-in-place control, so a
misclassified upload can be fixed without deleting and re-uploading it.

## Open questions / not yet done

- **Settings-page Ollama config isn't fully wired up.** The host/model/
  temperature fields on the Settings page only affect a degraded fallback
  path - the main `ChatEngine`'s `OllamaClient` (used for the actual
  RAG/structured chat flow) is constructed once, independently, and doesn't
  read those settings back.
- **No real tokenizer.** All budget math (`estimate_tokens`,
  `CHARS_PER_TOKEN_ESTIMATE`) is chars/4, not a model-accurate tokenizer.
  Good enough to prevent gross overflow, not exact.
- **No session rename UI.** Sessions are auto-titled from their first
  message (or "Previous Chat" for the migrated legacy one); there's no way
  to rename a session after the fact.
- **No cross-session search.** Each session's history is a separate vault
  key with no index over message content - finding "that thing I asked
  about three chats ago" isn't supported.
- **Dashboard spend totals are bill-`total`-only.** `spend_by_category`/
  `spend_over_time` sum `extraction["total"]` for bill-like categories;
  they don't attempt line-item-level aggregation or handle a document with
  a partial/missing `total`.
